## Implementation findings

**High — stored cost is not authoritative consistently.** `rbl_partial_acceptance.cpp:14` computes final arrival excluding terminal goal waits; checked subtraction and addition correctly implement U from current incumbent (`rbl_resumable_engine.cpp:1017`, :1034). However initialization :58–69, `computeCost` :80, ordinary acceptance and external trajectory updates use path length minus one and 32-bit sums. Recovery :1216 subtracts authoritative gain from that possibly different stored total instead of publishing validated candidate_soc. Audit probe reproduces valid stored/authoritative costs **220/218 before, 218/216 after** a successful gain-2 commit, in both Release and sanitizers. Validation cache records the version without checking cost consistency. The pilot's saved final paths all match reported cost, so this is a supported-input correctness gap, not evidence that those 192 final costs are wrong. Extreme path sizes/SoC can also narrow or overflow the remaining int arithmetic; checked 64-bit U does not solve the entire engine's arithmetic contract.

Verified code behavior:

- Candidate extraction validates IDs, uniqueness, endpoints, grid moves and computes fresh current-incumbent arrival costs. It retains negative candidates. U sums positive weights with checkedAdd; overflow fails INVALID_INPUT. U=0 returns before pairwise replacement collision checking or dependency graph construction (:1049–1070), though extraction/copying/route checks already cost time.
- `buildDependencyGraph` (`rbl_partial_acceptance.cpp:268`) compares each new route with every other old route. Collision creates dependency if a replacement exists; otherwise forbids the candidate. Reverse propagation excludes dependents of forbidden nodes. Replacement-to-replacement collision causes whole-input rejection, not optimization over conflicting alternatives. This is safe and appropriate to the supported pairwise-compatible prefix contract, but can discard feasible subsets of arbitrary colliding input.
- Exact maximum-weight closure uses Dinic with checked capacities and closure invariants (:512). Cycles are allowed: all members must be selected together with dependencies, and total gain determines benefit. Greedy (:807) sorts positive candidates and adds profitable transitive closures, including negative dependencies. Greedy is not generally exact.
- **Actual selective online selector is GREEDY_DEPENDENCY**, from profiler :275–290, engine header :130–149, and all 128 recovery-enabled raw labels. Dinic is an implemented alternative and unit-test target, not this pilot's selector.
- Ordinary interruptions retain completed-prefix checkpoints; resumption :630 onward revalidates constraints, rebuilds reservations, and restarts the unfinished agent deterministically. The checkpoint does **not** preserve low-level OPEN/CLOSED frontier structures; documentation discussing full frontier resumption must not imply that it does.
- Stale recovery candidates are evaluated against current incumbent on every call. Terminal recovery sorts checkpoint IDs FIFO (:1295), not descending gain, and reevaluates after each commit. Checkpoint-version freshness and search-state compatibility are distinct from completed-path reuse.
- `findEvictionVictimSlot` (`rbl_checkpoint.hpp:166`) matches unchanged saveCheckpoint reuse/FIFO rules for supported capacity 0–2. Fresh repair :473 calls recovery on that victim, then performs the original save regardless of recovery failure. Hook does not recursively save or mark victim committed. **Gap:** hook is gated by incoming `r_done>0`; an incoming zero-prefix checkpoint can overwrite a profitable victim without recovery, contrary to a broad “every eviction” claim.
- Complete recovery validation (:1165) constructs a complete plan and calls an occupancy-based validator independent of selector and dependency graph. External `rbl_validate` is a separate implementation. It checks discrete MAPF validity, not physical vehicle dynamics.
- Expected version, positive gain and deadline are checked before mutation. Normal failure returns before publication. Successful publication deletes old reservations, inserts new routes, updates paths and per-agent versions, then global cost/version/cache. This is a single-thread sequence, **not exception-safe atomic swap**: vector/allocation failures during publication have no rollback, and there is no post-publication deadline guard. “All failure modes preserve every state field” is unverified and too broad. Padded-cost inconsistency is demonstrated above.

## Deadline accounting

Profiler :260 initializes/loads and validates the initial plan **outside** the controlled-refinement budget. `steady_clock` starts :310, before RNG setup, agent-vector and anytime-trajectory setup. Global deadline is start+B. Loop checks reserve before checkpoint selection and before execution (:328–352). Baseline, every-filtered and eviction-only reserve 0.5 ms; terminal policies and TERMINAL_RESERVE_CONTROL use 2 ms. Control has the same cutoff calculation and does not run terminal recovery. Minimum effective slice is 1 ms, so the reserve is an approximate stopping target, not an exact boundary.

Within measured refinement time: extraction, filtering, candidate copies, compatibility, sorting, graph construction, selection, recovery validation, commit, checkpoint bookkeeping and terminal processing. Many expensive loops (route scans, dependency graph, whole-plan validation, copies, publication) do not poll internally. Selector checks are cooperative. Low-level search checks wall time every 64 expansions and at agent boundaries (`rbl_search_budget.hpp:175`); graph/validation scans remain non-preemptive. An operation can start before deadline and finish afterward. Final precommit check rejects work already late; it cannot guarantee publication finishes by deadline.

`total_solve_time_s` stops at profiler :398. **Outside** this time: final path serialization, final internal/external validation (:413 onward), telemetry aggregation/printing, result JSON and teardown/actual process return. Consequently it is refinement-loop elapsed wall time, not solver-return latency or all-finalization latency. No CPU timer is used for these claims.

Deadline cost is derived from timestamped trajectory points <=B (:403–410); final_cost is the returned incumbent, kept separately. All 192 recorded deadline costs equal final costs and reproduce from trajectories; no recorded late point is credited. However timestamps are captured after a repair returns, not at each exact publication. Eviction commits do not change the enclosing INTERRUPTED outcome and hence are not immediately logged as improvements. Multiple terminal commits get one timestamp after the whole terminal pass. These can **under-credit** a valid solution available earlier; exact best-valid-by-deadline accounting for those paths is UNVERIFIED, not disproved by zero natural commits here. Current tests do not exercise these boundary cases.

The 2 ms reserve is a fixed default/config value. No calibration dataset or tail bound linking 2 ms to worst-case extraction+validation+publication+return was found. Observed terminal work is tiny and no terminal commits occur, so this pilot does not stress reserve sizing. A general-purpose OS and cooperative checks provide no hard real-time guarantee.

Terminal policies: terminal-only **32 calls, 10 examined, 10 U=0**; combined **32 calls, 13 examined, 12 U=0**. Total **64 calls, 23 examined, 22 U=0, one non-skipped, zero commits**. Zero eviction recovery attempts are recorded for the 64 eviction-enabled runs. No direct capacity-eviction count is exported; the analysis substitutes attempts for that counter. Source scheduling always resumes a surviving checkpoint before fresh work; resumption updates the same slot, making capacity eviction absent under this scheduler/empty initial store. This is a code-based explanation, not evidence that eviction opportunities are impossible generally. Thousands of **stagnation discards** are recorded (e.g. 5,061 baseline; 4,905 eviction-only), which are different from store-capacity evictions and do not invoke this recovery hook.

Cumulative recovery gain measures decreases relative to each policy's own intermediate incumbent, not advantage over the baseline's eventual incumbent. The baseline can obtain the same gain through resumed full repairs; recovery also changes future search paths and consumes wall time. Filtered has −1,966 total iterations (**−61.4375 per run**) but **+370,441 total expansions**, so a simple causal “61 lost iterations caused all losses” is not established. ## Timing and overhead

Recorded every-filtered totals: filter **2,324.228 µs**, extraction **438,352.989 µs**. Divide by 162,396: **14.3121 ns filter**, **2.699284 µs extraction**, **2.713596 µs combined preparation**. Actual total measured PA wrapper overhead is **660,373.409 µs = .660373 s**, **4.066439 µs/evaluation**, **20.6367 ms/run**, across 96 seconds of nominal policy budgets. Extraction alone .438353 s is a total across 32 runs, not per-run time; none is CPU time. Wrapper timing excludes subsequent history insertion and some caller copies, so even .660 s is not every byte of recovery-related work.

Source :1031–1040 brackets **each call** with steady_clock, then sums elapsed values. It does not time one batch containing 162,396 untimed calls. Inputs are already assembled weights, at most neighborhood k=8 candidates; result is consumed by branch/counters, so dead-code removal of all work is not supported. Clock quantization/timer overhead prevent interpreting 14.3 ns as accurately measured isolated latency. Audit clock probe confirms this host's 125/3 ns mach tick (41.6667 ns) and many zero differences for back-to-back clock reads. Historical compiler/machine and binary cannot be attested from raw metadata; this current clock probe does not retroactively calibrate that run.

Historical exact policy: 203,260 attempts over 48 runs, **15.110770 s** total PA time; mean **74.3421 µs**, **median of 48 per-run medians=62.187 µs**, fraction of 144 budget seconds **10.49359%**. So ~62 µs is not graph-only cost or the overall average. Comparing that median-of-medians/full pipeline/exact selector to 2.71 µs mean/preparation-only/greedy selector on a different 32-cell workload does **not verify a 95.6% like-for-like overhead reduction**. The arithmetic percentage is reproducible; the comparative performance claim is not. Historical greedy mean is 74.1744 µs and median-of-medians 61.8955 µs; still not a controlled same-workload comparison. No measured basis proves the 2 ms reserve bounds worst-case work or process return.

## Final answers and prioritized fixes

1. **What the implementation actually does:** preserves completed-prefix repair checkpoints, restarts unfinished agents, optionally filters current-incumbent replacement gains and runs greedy dependency-closure recovery on interruptions, capacity eviction, or FIFO terminal checkpoints. An exact Dinic selector also exists. It independently validates a complete discrete plan before recovery publication, with cooperative time checks and the stored-cost caveat above.
2. **Does raw evidence support improvement over resumption?** No. Selective trigger variants/control tie all 32 pairs; every-interruption recovery loses four and wins none. This is no demonstrated benefit on the tested data, not proof of equivalence or universal uselessness.
3. **Are tests and timing claims reproducible?** Current 10/10 suites pass in true Release and ASan/UBSan; meaningful coverage is narrower than reported. Raw totals reproduce, but the advertised sanitizer command, original raw manifest, Wilcoxon p label, comparable 95.6% reduction, 192-zero-overrun claim and hard deadline guarantee do not. Exact historical build provenance and deadline-return guarantees remain unverified.
4. **Remaining fixes in order:** (P1) unify engine costs on checked authoritative arrival SoC, publish candidate_soc consistently, test padded paths and overflow; (P1) define transaction failure scope and stage complete reservations/paths/versions/caches before publication or provide rollback; (P1) record every commit completion and best-valid-before-deadline, separate cutoff/refinement/return/finalization clocks, remove hard guarantees and bound/poll costly stages; (P2) fix raw manifest after final serialization and record source tree, binary, compiler, fixture hashes and exact run commands; (P2) add deterministic cancellation/compatibility-changing cascade/K=2 victim/real eviction-hook/conflicting-route/reservation-cache assertions; cover zero-prefix incoming eviction; (P2) fix unsupported sanitizer option and statistical fallback, report SD/SEM/alternatives/dependence accurately; (P2) reconcile all narrative tables, selector, FIFO, denominators, timing boundaries and snapshot claims; (P3) only then run a predeclared sequential matched diagnostic pilot and comparable end-to-end overhead measurement, before any untouched confirmation study.
